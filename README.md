# ServiceNow SLA Risk Predictor

Predict which ServiceNow tickets are likely to breach their SLA — **before** they breach — so support teams can escalate, reassign, or staff up in time.

> **Synthetic data only.** Every ticket in this project is generated from hand-written templates with a fixed random seed. No real employer data, no real ticket data, no personal data.

## The problem (in plain language)

A support desk handles thousands of tickets. Each ticket has a deadline (its SLA): P1 tickets must be resolved in 4 hours, P2 in 8, P3 in 24, P4 in 72. When a ticket misses its deadline it is an **SLA breach** — the user waits too long, the business process stalls (for example, an SAP purchase order stuck in approval blocks procurement), and the team gets penalised.

Today, teams only find out about a breach *after* it happens. This project flips that around: it learns from past tickets which ones are risky — high priority, certain assignment groups, certain keywords ("urgent", "production down", "stuck in approval"), long queues — and flags them while there is still time to act.

**Business impact:** earlier escalation of the riskiest ~10% of tickets, shorter queues for P1/P2 work, and a clear view of which groups (e.g. SAP Support, Database) carry the highest breach rates so managers can staff accordingly.

## Dataset

- **3,000 synthetic tickets** (`data/tickets.csv`, plus a 100-row `data/tickets_sample.csv`), generated by `src/generate_data.py` with seed 42.
- ~40 hand-written realistic templates across Incident / Request / Problem — e.g. "VPN not connecting", "Laptop screen flickering", "Password reset", "SAP MM purchase order stuck in approval" — with wording variations.
- Columns: `ticket_id`, `short_description`, `category`, `subcategory`, `priority` (P1–P4), `channel` (Portal/Email/Phone/Chat), `assignment_group` (Network, Hardware, Service Desk, SAP Support, Database, Security), `opened_at`, `resolved_at`, `resolution_hours`, `queue_hours`, `sla_breach`.
- Overall breach rate: **30.6%** — P1 63.9%, P2 46.6%, P3 26.0%, P4 17.3%.
- Breach is probabilistic, driven by priority, assignment group, high-risk keywords and queue time, so the signal is learnable but not trivial (no single field gives it away).
- Supporting tables: `assignment_groups` (6 groups), `sla_policy` (P1 4h, P2 8h, P3 24h, P4 72h).

## How to run

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

python src/generate_data.py   # creates data/tickets.csv (3,000 rows)
python src/load_to_db.py      # loads CSVs into data/tickets.db + creates views
python src/train.py           # trains model, writes results/metrics.json + docs/*.png
streamlit run app.py          # dashboard at http://localhost:8501
```

The dashboard works from the CSVs in `data/` if the `.db` or model file is missing, and tells you to run the pipeline first when data is absent.

## Model

**TF-IDF (description + category + subcategory + priority + group + channel) + Logistic Regression** (`class_weight="balanced"`), saved as a scikit-learn `Pipeline` with joblib so the dashboard can reuse it for live triage. Real stratified 80/20 train/test split (2,400 train / 600 test).

### Results (actual run, 11 Nov 2026)

| Metric | Value |
|---|---|
| Accuracy | 0.658 |
| Precision | 0.458 |
| Recall | 0.620 |
| F1 | 0.527 |
| ROC-AUC | 0.686 |
| Breach rate (test set) | 0.306 |

Recall is deliberately favoured over precision (balanced class weights): missing a ticket that will breach is costlier than flagging one that won't. Full numbers live in `results/metrics.json`. The modest scores are honest — the synthetic breach signal is noisy by design, and text alone cannot capture queue dynamics perfectly. See *Future improvements*.

## SQL highlights

MySQL-compatible DDL in `schema.sql` (tables `tickets`, `assignment_groups`, `sla_policy`); analytical views/queries in `sql/queries.sql`, also created in SQLite by `src/load_to_db.py`:

- **MTTR by group** — `vw_mttr_by_group`: average resolution hours, average queue hours and breach rate per assignment group.
- **Breach rate by priority/category** — `vw_breach_rate_by_priority`.
- **Monthly breach-rate trend** — `vw_breach_trend_monthly`, plus ad-hoc queries for worst queues and breach rate by channel.

Example:

```sql
SELECT assignment_group,
       ROUND(AVG(resolution_hours), 2) AS avg_resolution_hours,
       ROUND(100.0 * SUM(sla_breach) / COUNT(*), 1) AS breach_rate_pct
FROM tickets
GROUP BY assignment_group
ORDER BY avg_resolution_hours DESC;
```

## Dashboard

`streamlit run app.py` gives you:

- **KPI cards** — ticket count, breach rate, average resolution and queue time (all respond to the sidebar filters).
- **Breach-risk queue** — every ticket scored by the saved model, sorted by predicted risk, with an actionable recommendation per ticket (escalate / reassign / monitor).
- **Charts** — breach rate by priority, monthly breach-rate trend, MTTR by assignment group.
- **Live triage demo** — type or paste a ticket description, pick category / priority / group, and get a predicted breach risk with a recommended action.
